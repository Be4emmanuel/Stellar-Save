# ADR-006: Workspace Package Manager — pnpm

**Status**: Accepted  
**Date**: 2026-10-18  
**Author**: Stellar-Save Team  
**Deciders**: Engineering Team  
**Related issue**: #1834, #106

---

## Context

The repository is a multi-package monorepo with four workspaces:

| Workspace | Directory |
|-----------|-----------|
| Frontend  | `frontend/` |
| Backend   | `backend/` |
| Mobile    | `mobile/` |
| SDK / Packages | `packages/*` |

Two lockfiles co-exist in the repository, causing inconsistency:

- `/pnpm-lock.yaml` — root-level pnpm lockfile covering all workspaces
- `/package-lock.json` — root-level npm lockfile (stale, not reflecting real installs)
- `/frontend/package-lock.json` — workspace-level npm lockfile (stale)
- `/backend/package-lock.json` — workspace-level npm lockfile (stale)

The root `package.json` already declares `"packageManager": "pnpm@9.0.0"` and a `pnpm-workspace.yaml` defines all workspace members. The pnpm lockfile is the one that reflects actual installs from the CI pipeline and developer machines.

The stray `package-lock.json` files were generated by contributors who ran `npm install` instead of `pnpm install`. Without a recorded decision, new contributors will continue generating incorrect lockfiles and pushing drift.

### Why pnpm was adopted

1. **Workspace protocol** — pnpm's native workspace protocol (`workspace:*`) lets `packages/sdk` be referenced by `frontend` and `backend` without symlink hacks.
2. **Disk efficiency** — pnpm uses a content-addressable store. In a monorepo with shared dependencies across four packages, this significantly reduces `node_modules` size.
3. **Strict hoisting** — pnpm prevents "phantom dependency" bugs (using a package that is not declared in your own `package.json`) by default.
4. **Speed** — Parallel installs and hard-linking from the store make `pnpm install` measurably faster than `npm install` in CI.
5. **Turbo compatibility** — The project uses Turborepo (`turbo.json`) for build orchestration; Turbo has first-class support for pnpm workspaces.
6. **Version pinning** — `"packageManager": "pnpm@9.0.0"` in `package.json` ensures every developer and CI run uses the same pnpm major/minor/patch version via Corepack.

### Alternatives considered

| Tool | Reason not chosen |
|------|------------------|
| npm workspaces | Slower installs, no content-addressable store, weaker hoisting controls. Also, the pnpm lockfile already existed and reflects current state. |
| Yarn Berry (v3+) | Plug'n'Play is incompatible with several native addons in the mobile workspace. Zero-installs would add large binary blobs to the repository. |
| Yarn Classic (v1) | End-of-life, security-only maintenance mode, no improvements planned. |

---

## Decision

**pnpm@9 is the single, authoritative package manager for this repository.**

- `pnpm-lock.yaml` is the canonical lockfile. It must be committed and kept up to date.
- All `package-lock.json` files at root, `frontend/`, and `backend/` are legacy artefacts and must be removed (tracked in issue #106).
- Developers must use `pnpm` for all install, add, and remove operations.
- CI must use `pnpm` via Corepack or a direct install step.

---

## Consequences

### Positive

- A single lockfile strategy eliminates merge conflicts from competing lockfiles.
- New contributors get a clear, enforced rule from day one.
- Strict hoisting surfaces missing dependencies at install time rather than at runtime.

### Negative / Migration notes

- Developers who have `npm` or `yarn` muscle memory need to switch commands:

  | Old (npm)           | New (pnpm)           |
  |---------------------|----------------------|
  | `npm install`       | `pnpm install`       |
  | `npm install X`     | `pnpm add X`         |
  | `npm install -D X`  | `pnpm add -D X`      |
  | `npm run <script>`  | `pnpm run <script>` or `pnpm <script>` |
  | `npm ci`            | `pnpm install --frozen-lockfile` |

- The `package-lock.json` files must be deleted before merging any PR that touches dependencies (tracked in #106).
- `.gitignore` should be updated to reject `package-lock.json` commits if it is not already.
