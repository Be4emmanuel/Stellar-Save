# ADR 00XX: zk/ Subsystem Architecture and Trust Assumptions

## Context

The `zk/` directory implements the zero-knowledge proof flows used by the
protocol. It is split into three cooperating parts:

- `zk/circuits` — circuit definitions and the artifacts (R1CS / WASM / zkey)
  produced by the circuit build pipeline.
- `zk/client` — proof generation: witness construction and proving on the
  client side.
- `zk/server` — proof verification: verifying submitted proofs and exposing the
  verification result to the rest of the system.

Until now there has been no architectural documentation, which makes security
review and onboarding difficult. This ADR records the end-to-end flow, the
trust assumptions, and the contracts that consume zk proofs.

## Decision

We document the zk subsystem as described below. This ADR is descriptive of the
current design; it does not change behavior.

### 1. Proof generation / verification flow (end-to-end)

1. **Circuit definition (`zk/circuits`)**
   - The circuit is defined in `zk/circuits` and compiled by the circuit build
     pipeline into the proving artifacts (WASM witness calculator + proving key)
     and the verification key.
   - The verification key is the only circuit artifact the verifier needs; the
     proving artifacts are used by the client.

2. **Witness construction (`zk/client`)**
   - The client collects the private inputs (witness) and the public inputs
     (public signals) required by the circuit.
   - Inputs are validated/normalized before being passed to the prover so that
     malformed inputs fail early rather than producing an invalid proof.

3. **Proof generation (`zk/client`)**
   - The client runs the prover with the compiled circuit, the proving key, and
     the witness to produce a proof plus the public signals.
   - The resulting `{ proof, publicSignals }` payload is the unit that is
     transmitted to the verifier.

4. **Proof submission**
   - The proof payload is submitted to the verifier (via `zk/server` and/or
     on-chain, depending on the consumer — see section 4).

5. **Proof verification (`zk/server`)**
   - The verifier loads the verification key for the circuit and verifies the
     proof against the public signals.
   - Verification is deterministic and stateless with respect to the prover:
     the verifier only needs the verification key and the submitted
     `{ proof, publicSignals }`.
   - The verification result (accept/reject) is returned to the caller; a
     rejected proof must not be treated as a valid statement.

### 2. Trust assumptions

- **Soundness** relies on the underlying proving system and on the circuit
  correctly encoding the intended statement. A bug in the circuit definition
  invalidates the security argument even if proofs verify.
- **The verification key is trusted.** The verifier must use the verification
  key that corresponds to the deployed circuit. A mismatched or attacker-supplied
  verification key breaks soundness.
- **Public signals are bound to the proof.** The verifier must check the public
  signals it cares about (e.g. the expected commitment/root/address); verifying
  a proof without binding the relevant public inputs does not establish the
  intended statement.
- **The prover is untrusted.** The client is assumed to be adversarial; it may
  submit arbitrary proofs and public signals. All validation happens on the
  verifier side.
- **Witness secrecy.** Private inputs are only known to the client; they are not
  transmitted to the verifier. Any leakage of witness data outside the prover is
  a confidentiality failure.
- **Artifact integrity.** Proving and verification artifacts must be built from
  the reviewed circuit source and distributed through a trusted channel; a
  tampered proving key can enable forged proofs.

### 3. Trusted setup

- If the circuit uses a proving system that requires a trusted setup (e.g. a
  Groth16-style ceremony), the resulting parameters are a trust assumption:
  whoever participated in / controlled the setup could, if the ceremony was not
  secure, forge proofs.
- The setup artifacts (proving key / verification key) must be generated by the
  documented circuit build pipeline and pinned/committed so that reviewers can
  verify which parameters are in use.
- If the circuit uses a transparent setup (no trusted ceremony), record that
  explicitly here so reviewers do not assume a ceremony is required.

## Consequences

- Security reviewers and new contributors have a single entry point describing
  the flow, the trust assumptions, and the consumers.
- Any change to the circuit, the verification key, or the set of consuming
  contracts must update this ADR.
